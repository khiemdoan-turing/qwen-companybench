Why most of this run has no result

A Harbor agent-setup bug, not a Qwen finding.

The environment setup step for each trial installs tmux and asciinema. When the apt-get install path doesn't take, the setup script falls back to compiling tmux from source inside the container. That fallback fails, and when it fails the trial never gets a terminal session:

Installing tools using apt-get: ... apt-get install -y tmux asciinema Installing tmux from source... Failed to install tmux from source Installing asciinema via pip... asciinema successfully installed using pip Trial 142553__fccX2Kg failed: Failed to start tmux session. Error: None Collecting main service artifacts Not retrying trial because the maximum number of retries has been reached

Quoted verbatim from job.log for job 142553_1_main (kiem-sandbox:/root/pq/qwen/companybench_batch/jobs_main/142553_1_main/job.log). This exact "Installing tmux from source... Failed to install tmux from source" sequence appears in 39 of 161 logged attempts so far (ssh kiem-sandbox grep -l, this session). The disk-pressure explanation sometimes given for why apt-get falls back to a source build is not independently confirmed: no job log contains "No space left on device" or similar, and the driver's own free-disk reading was 100+ GB free through almost the entire run (one single 0.0GB reading appears at the very start of this driver's ramp-up, not sustained and not correlated with the 71 infra failures spread across the run). Treat the redundant install step as the confirmed mechanism and disk pressure as an unconfirmed hypothesis. Compare: task 142637 (T38)'s successful trial installed tmux via apt-get directly with no fallback and no failure.

This is an infrastructure limitation in how trials get provisioned, not a measurement of what Qwen 3.8 Max can or can't do on CompanyBench. Tasks that got a working terminal session score like any other run; tasks that didn't never reach the agent at all.

Method

What this page is, and is not.

Denominators

  • 40 tasks, Data OS dataset 1732, same set as Gemini 4 Argon and Grok 4.7.
  • Target k=3 trials per task: 1 at an 80-minute agent budget, a 5-hour rerun for any trial that didn't finish with a scored result in 80 minutes.
  • 120 target trials. 18 are real-scored (ok/timeout) as of this build. 161 logged attempts have been recorded in total (both CSVs, includes retries).
  • No cost figures on this page or in this site's data files, by policy; internal cost tracking lives in the internal report, not here.

What this does not establish

  • Not a finished benchmark pass: 25 of 40 tasks have zero real-scored trials right now.
  • Not a capability verdict on the 2 full-marks results (T22, T32) or the 13 zero results: each is a single trial, and a single trial is not a rate.
  • Not evidence Qwen is worse at CompanyBench than the peer models shown: the peer runs are complete (120 of 120 scored trials each); this run is 18 of 120. The gap in full-marks rate is as likely to reflect which trials happened to get a working terminal as anything about the model.
  • The T38 side-by-side (page section above) is the one place with equal footing: all 6 models have all 3 trials scored on the same task_id. Qwen is the only one at 0.00 there.

Run policy

  • Model: Qwen 3.8 Max, OpenRouter qwen/qwen3.8-max-prime, via Harbor terminus-2.
  • reasoning_effort high, internet on, web search off.
  • Long reruns are picked from a fixed priority queue (LONG_RERUN_PRIORITY in run_batch_v9.py), not resampled; a task that reaches k on the 80-minute pass is not rerun.

Provenance

  • This page: built 2026-10-28 from a live pull of the sandbox CSVs and job logs, in a new local directory, not yet published.
  • Qwen trace data: masked locally in this build (emails, URLs, the benchmark corpus's name, 3+ digit numbers and quoted literals replaced; no task-specific grader values were available to extract for this task, so the masking is the strict fallback, not a per-task targeted one).
  • Peer (Gemini, Grok) numbers: read from their own already-published sites, not re-derived.
  • Task title and category ("Card decline alert coverage audit", "Cards and card controls") and the task prompt text: reused verbatim from the already-published, already-masked prompts40.json used to build the Gemini site, since it is the identical task.
